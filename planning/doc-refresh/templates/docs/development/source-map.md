# Source map: scientific objects to executable tests

| Question | Start here | What to look for |
|---|---|---|
| Which scientific objects are distinguished? | [core contracts](../../{{P_CORE}}) | Quantity, observation, identity/provenance and state roles. |
| How are supplied alternatives updated? | [finite candidates](../../{{P_INFERENCE}}) | Whole joint state–mechanism alternatives and evidence history. |
| Where does a system become executable? | [assembly](../../{{P_ASSEMBLY}}) | Cellerator-backed numerical ownership rather than duplicated kernels. |
| Where are supported capabilities checked? | [native foundation tests](../../{{P_TESTS}}) | Distinct contracts and numerical/semantic checks. |
| Where is the complete-program measurement? | [benchmark source](../../{{P_BENCH}}), [recorded methodology](../../{{P_BENCH_REPORT}}) | Finite lifecycle, full outputs/responses and limited activity semantics. |
| How are replay and Python connected? | [replay](../../{{P_REPLAY}}), [binding](../../{{P_BINDINGS}}), [Python layer](../../{{P_PYTHON}}) | Actual supported boundary, not an inferred universal package design. |

The [build graph](../../{{P_CORE_CMAKE}}) now distinguishes a real current foundation from legacy sketches. Retain old experiments under a clearly marked legacy/experimental area only after checking remaining consumers. A stale historical map is not evidence that a current CMake target is archaeological.
