# Optional Cellerator work, no artificial cross-ledger dependencies

GH and CE remain independent Todo/Git authorities. The GH native plan contains no foreign task IDs. The optional CE plan contains only `CE-L1-ENABLE` and its aggregate. Do not import it simply because it is present.

## Select the route

During `GH-L1-LEARN`, run a bounded native capability check for the selected family's complete objective/parameter-gradient path. If current installed CE supplies the needed operations and derivatives, record the tested identity and continue without a CE import.

Otherwise record one compact demand in `planning/learning-v1/runtime/ce-demand.json` under the active GH task: selected scientific operation, forward/response actions, shapes/axes/precision, missing route, proposed existing owner and native acceptance example. Do not hand CE an abstract request to build a general ML framework.

Copy this package into the CE planning directory (without overwriting existing material), then use its own current authority:

```sh
cd <Cellerator>
python3 planning/learning-v1/scripts/check_package.py
project-control plan validate --project cellerator \
  --file planning/learning-v1/machine/cellerator.optional.todo-plan.json
# Review current target-specific preview/diff, then:
project-control plan apply --project cellerator \
  --file planning/learning-v1/machine/cellerator.optional.todo-plan.json
```

Explicit CE run focus is `CE-L1-RUN-V1`. Use an independent CE claim/session or first-class agent. A GH bounded child does not gain CE write authority from a prompt or this document. The main thread coordinates scientific intent and producer/consumer acceptance; no extra architecture agents are needed by default.

CE completes the bounded native implementation and supplies source, installed package/build identity and executed tests. GH verifies the installed consumer against that exact delivery. Demand can precede completed GH learning; CE does not wait for the consumer it is enabling to finish. This prevents a circular dependency.

One small receipt is sufficient. Suggested producer fields are `route`, `producer_commit`, `package_identity`, `implemented_capabilities`, `test_evidence` and `limitations`; GH adds `consumer_evidence`. This is ordinary project evidence, not a second workflow authority or cross-project transaction. Do not fabricate an empty receipt in advance or mistake a producer commit alone for validated consumption.

Final GH acceptance depends on the **chosen** route: verified reuse, or a qualified producer plus tested consumer. It never waits for both hypothetical branches. If broader interfaces need amendment, use supported local plan/interface actions with current evidence, not a copy of another authority's database or a custom runtime patch.
